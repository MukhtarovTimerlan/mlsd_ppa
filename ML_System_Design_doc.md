# ML System Design Doc - [RU]
## Дизайн ML системы - California Housing Price Prediction

## 1. Цели и предпосылки

### 1.1. Зачем идем в разработку продукта?

- **Бизнес-цель (Product Owner):** Добавить на сайт по купле/продаже недвижимости новую функцию — «Онлайн-оценка стоимости дома». Это позволит потенциальным продавцам быстро получить примерную рыночную стоимость своего объекта без необходимости обращения к специалисту.
- **Почему станет лучше, чем сейчас, от использования ML (Product Owner & Data Scientist):** В текущем процессе оценка выполняется специалистами вручную, что занимает значительное время (от нескольких часов до дней) и требует вовлечения персонала. Внедрение ML-модели позволит:
    - Автоматизировать процесс и сделать его мгновенным (до 1 секунды).
    - Снизить нагрузку на специалистов, оставив за ними только сложные или нестандартные объекты.
    - Повысить лояльность пользователей за счет полезного бесплатного инструмента.
- **Что будем считать успехом итерации с точки зрения бизнеса (Product Owner):** Успехом итерации является создание работающего прототипа сервиса, способного выдавать предсказания с приемлемой точностью. Метрика успеха: **Медианная абсолютная ошибка (MAE) модели не превышает 0.5 (в логарифмированном масштабе цен), что примерно соответствует отклонению в 15-20% от реальной цены для большинства объектов**. Прототип должен быть готов к демонстрации стейкхолдерам.

### 1.2. Бизнес-требования и ограничения

- **Краткое описание БТ (Product Owner):**
    -  Сервис должен принимать на вход основные характеристики объекта недвижимости (доход населения, возраст жилья, количество комнат, население, координаты и т.д.).
    -  Сервис должен возвращать предсказанную медианную стоимость дома в формате JSON.
    -  Взаимодействие с сервисом должно осуществляться по HTTP (REST API).
- **Бизнес-ограничения (Product Owner):**
    - **Срок:** Решение должно быть разработано за 2 дня (до 06.03.2025).
    - **Технологии:** Использовать только open-source библиотеки и инструменты (Python, scikit-learn, FastAPI и т.д.).
    - **Инфраструктура:** Решение должно быть легковесным и запускаться на локальной машине или минимальном облачном сервере (без требований к высоким нагрузкам).
- **Что мы ожидаем от конкретной итерации (Product Owner):** Получить MVP (Minimum Viable Product), который включает в себя исследовательский анализ данных, обученную модель и API-сервис для взаимодействия с ней.
- **Описание бизнес-процесса пилота (Product Owner):** На этапе пилота процесс выглядит следующим образом:
    1.  Пользователь на сайте заполняет форму с характеристиками своего дома.
    2.  Эти данные отправляются на наш ML-сервис (API).
    3.  Сервис возвращает предсказанную стоимость.
    4.  Предсказание отображается пользователю на сайте.
- **Что считаем успешным пилотом? Критерии успеха и возможные пути развития проекта (Product Owner):**
    - **Успех пилота:** Демонстрация стабильной работы API на тестовых запросах и достижение целевой метрики качества (MAE ≤ 0.5) на отложенной тестовой выборке.
    - **Пути развития:**
        1.  Сбор обратной связи от пользователей и специалистов.
        2.  Расширение набора признаков (например, добавление данных о районе, этаже, материале стен).
        3.  Улучшение модели (переход на более сложные алгоритмы, ансамбли).
        4.  Разработка простого веб-интерфейса (фронтенда) для демонстрации.
        5.  Внедрение системы мониторинга качества предсказаний.

    - Автоматическое переобучение модели на новых данных (ML pipeline).
    - Логирование запросов и предсказаний.
    - Более глубокая оптимизация гиперпараметров.
    - Контейнеризация (Docker) для упрощения деплоя.

### 1.4. Предпосылки решения

- **Описание всех общих предпосылок решения (Data Scientist):**
    - **Данные:** Используется открытый датасет **California Housing**. Данные содержат информацию по блокам кварталов (block groups) Калифорнии на основе переписи 1990 года. Это стандартный и хорошо изученный набор данных для задач регрессии.
    - **Гранулярность модели:** Уровень прогноза — квартал (блок). Модель предсказывает медианную стоимость дома в данном квартале.
    - **Горизонт прогноза:** Прогноз на текущий момент (исторические данные используются для обучения, модель оценивает стоимость на момент сбора данных). Временной ряд не строится.
    - **Признаки:** Используются все 8 числовых признаков, предоставленных в датасете (`MedInc`, `HouseAge`, `AveRooms`, `AveBedrms`, `Population`, `AveOccup`, `Latitude`, `Longitude`). На этапе EDA будет принято решение о необходимости создания новых признаков (feature engineering).
    - **Целевая переменная:** `MedHouseVal` (медианная стоимость дома в сотнях тысяч долларов). В датасете целевая переменная уже была подвергнута логарифмированию (каппингу) для ограничения выбросов, что является преимуществом.

**2. Методология Data Scientist**

### 2.1. Постановка задачи

С технической точки зрения решается задача **регрессии** (обучение с учителем). Имеется набор исторических данных о квартирах (блоках кварталов) в Калифорнии, каждый объект описывается 8 числовыми признаками. Целевая переменная — медианная стоимость дома (`MedHouseVal`) в сотнях тысяч долларов.

Необходимо построить модель, которая по признакам объекта сможет максимально точно предсказать его стоимость. Модель будет использоваться в онлайн-режиме: пользователь отправляет характеристики объекта через API, сервис возвращает предсказание.

Задача включает в себя:
- проведение разведочного анализа данных (EDA) для понимания распределений, корреляций, наличия выбросов и пропусков;
- предобработку данных (стандартизация числовых признаков, возможно создание новых признаков);
- обучение baseline-модели (линейная регрессия);
- обучение основной модели (градиентный бустинг) с подбором гиперпараметров;
- оценку качества моделей на отложенной тестовой выборке с помощью метрик MAE, RMSE, R²;
- разработку REST API сервиса для инференса;
- демонстрацию работоспособности решения.

## 2.3. Этапы решения задачи Data Scientist

### Этап 1. Подготовка данных (EDA и предобработка)

**Данные и сущности**

Модель будет обучаться на открытом датасете **California Housing**, который содержит информацию о 20 640 квартальных блоках (block groups) Калифорнии по данным переписи населения 1990 года. Данные включают 8 числовых признаков и целевую переменную – медианную стоимость дома в блоке.

**Таблица признаков**

| Название данных | Описание | Есть ли данные в компании | Требуемый ресурс для получения данных | Проверено ли качество данных |
|---|---|---|---|---|
| **MedInc** | Медианный доход в блоке (в десятках тысяч долларов) | Нет (публичный датасет) | DS | Да (известно отсутствие пропусков, но требуется проверка на выбросы) |
| **HouseAge** | Медианный возраст дома в блоке (в годах) | Нет | DS | Требуется проверка |
| **AveRooms** | Среднее количество комнат на домохозяйство | Нет | DS | Требуется проверка |
| **AveBedrms** | Среднее количество спален на домохозяйство | Нет | DS | Требуется проверка |
| **Population** | Население блока (количество человек) | Нет | DS | Требуется проверка |
| **AveOccup** | Среднее количество членов домохозяйства | Нет | DS | Требуется проверка |
| **Latitude** | Широта центра блока | Нет | DS | Требуется проверка |
| **Longitude** | Долгота центра блока | Нет | DS | Требуется проверка |

**Таблица целевой переменной**

| Название данных | Описание | Есть ли данные в компании | Требуемый ресурс | Проверено ли качество |
|---|---|---|---|---|
| **MedHouseVal** | Медианная стоимость дома в блоке (в сотнях тысяч долларов, с капом 5.0001) | Нет | DS | Требуется проверка распределения |

**Что делаем на этапе 1**

1. **Загрузка данных** из библиотеки `sklearn.datasets.fetch_california_housing` (или альтернативного источника).
2. **Первичный анализ (EDA):**
   - Проверка пропусков (в оригинале их нет, но имитируем проверку).
   - Описательные статистики (среднее, медиана, стандартное отклонение, квантили) для каждого признака и целевой переменной.
   - Визуализация распределений (гистограммы, box plots) для выявления скошенности и выбросов.
   - Корреляционный анализ (тепловая карта) для выявления мультиколлинеарности и связи признаков с целевой переменной.
   - Анализ географического распределения цен (scatter plot по координатам).
3. **Предобработка:**
   - При необходимости — обработка выбросов.
   - Создание новых признаков (feature engineering):
     - `rooms_per_household` = AveRooms / AveOccup (количество комнат на человека)
     - `bedrooms_per_room` = AveBedrms / AveRooms (доля спален)
     - `population_per_household` = Population / AveOccup (население на домохозяйство) — но AveOccup уже среднее, возможно, избыточно.
   - Стандартизация числовых признаков (StandardScaler) для линейной модели и для ускорения сходимости градиентного бустинга (хотя бустинг не требует масштабирования, но для единообразия можно применить).
   - Целевую переменную оставляем без преобразований (она уже ограничена сверху, лог-трансформация не требуется, но при желании можно рассмотреть для улучшения, однако это усложнит интерпретацию).
4. **Разделение данных** на обучающую, валидационную и тестовую выборки в пропорции 60/20/20. Так как данные не являются временным рядом, используем случайное стратифицированное разбиение по квартилям целевой переменной, чтобы сохранить распределение цен в каждой выборке.

**Результат этапа 1:**
- Jupyter ноутбук с EDA, визуализациями и выводами.
- Обработанный датасет, готовый для обучения (возможно, сохранённый в CSV или pickle).
- Объект StandardScaler, обученный на тренировочных данных, для последующей стандартизации новых данных при инференсе.
- Понимание ключевых зависимостей, которые помогут при выборе модели и интерпретации результатов.

**Риски этапа 1:**
- Выбросы могут сильно влиять на линейную модель; предусматриваем их анализ и возможное удаление/винзоризацию.
- Мультиколлинеарность (например, AveRooms и AveBedrms могут быть коррелированы) — для линейной модели это проблема, будем проверять VIF.
- Географические координаты могут требовать более сложной обработки (например, кластеризация), но в рамках пилота оставляем как есть.

### Этап 2. Подготовка прогнозных моделей

#### 2.1. Baseline (линейная регрессия)

**Цель:** получить простую интерпретируемую модель, которая послужит отправной точкой для сравнения.

**Формирование выборки:** используем те же обучающую и валидационную выборки, что получены на этапе 1. Тестовая выборка откладывается для финальной оценки.

**Горизонт, гранулярность, частота пересчёта:** модель даёт точечную оценку для блока; для пилота пересчёт не планируется, модель будет зафиксирована.

**Целевая переменная:** MedHouseVal (согласована с бизнесом как медианная стоимость дома в блоке).

**Метрики качества и связь с бизнесом:**
- **MAE (Mean Absolute Error)** – средняя абсолютная ошибка в сотнях тысяч долларов. Интерпретация: например, если MAE = 0.4, то в среднем модель ошибается на 40 000 $. С учётом средней цены около 200 000 $, это ~20% ошибки, что приемлемо для ориентировочной оценки.
- **RMSE (Root Mean Square Error)** – штрафует большие ошибки сильнее, полезно для понимания разброса.
- **R²** – доля объяснённой дисперсии; чем ближе к 1, тем лучше.

Для baseline не устанавливаем жёстких целевых значений, но ожидаем R² не ниже 0.5 (типично для линейной регрессии на этих данных ~0.6). Основная задача baseline – дать точку отсчёта.

**Техника решения:**
- Используем линейную регрессию (sklearn.linear_model.LinearRegression) как наиболее простой алгоритм.
- Обучение производится на стандартизированных признаках (StandardScaler из этапа 1).
- Гиперпараметры не настраиваем (по умолчанию).
- Оценка на валидационной выборке.

**Риски:**
- Линейная модель может не уловить нелинейные зависимости (например, влияние координат).
- Чувствительность к выбросам – планируем на этапе EDA обработать выбросы или рассмотреть робастные варианты (например, HuberRegressor), но baseline оставим обычную регрессию для простоты.
- Мультиколлинеарность – если будет обнаружена, можно применить гребневую регрессию (Ridge) как улучшение baseline, но в рамках пилота допустимо использовать обычную регрессию, предварительно удалив сильно коррелированные признаки.

**Необходимый результат этапа для baseline:**
- Обученная модель линейной регрессии.
- Значения метрик на валидации.
- Понимание, насколько сложная модель требуется.

#### 2.2. Основная модель (MVP) – градиентный бустинг

**Цель:** достичь более высокой точности предсказания за счёт использования сложного нелинейного алгоритма.

**Формирование выборки:** те же обучающая и валидационная выборки.

**Горизонт, гранулярность, частота пересчёта:** аналогично baseline.

**Целевая переменная:** MedHouseVal (без изменений).

**Метрики качества и целевые значения:**
- Цель: улучшить baseline по MAE минимум на 15-20% (например, с 0.45 до 0.35-0.38).
- Конкретное целевое значение: MAE ≤ 0.4 на тестовой выборке, что соответствует средней ошибке ≤ 40 000 $. Бизнес-интерпретация: пользователь получает оценку с точностью ±20% для большинства объектов, что достаточно для принятия решения о выставлении лота.

**Техника решения:**
- **Алгоритм:** XGBoost или LightGBM (выбор будет сделан после EDA, оба кандидата показывают хорошие результаты на табличных данных). Для определённости в дизайн-документе укажем XGBoost.
- **Признаки:** все признаки, включая созданные на этапе 1. Стандартизация для бустинга не обязательна, но может быть оставлена для единообразия пайплайна.
- **Кросс-валидация:** используем 5-кратную кросс-валидацию на обучающей выборке для подбора гиперпараметров. Так как данные не временные, можно применять обычную KFold.
- **Гиперпараметры для настройки:**
  - `n_estimators` (число деревьев)
  - `max_depth` (глубина деревьев)
  - `learning_rate` (темп обучения)
  - `subsample` (доля объектов для каждого дерева)
  - `colsample_bytree` (доля признаков)
  - `reg_alpha`, `reg_lambda` (регуляризация)
- **Метод поиска:** RandomisedSearchCV (ограниченное число итераций из-за времени) с последующей донастройкой вручную при необходимости.
- **Оценка:** после нахождения лучших параметров обучаем модель на всей обучающей выборке и оцениваем на валидационной. Финальное тестирование – на отложенной тестовой выборке.

**Риски:**
- Переобучение – контролируется с помощью валидации и регуляризации.
- Время обучения – при большом количестве комбинаций может быть долго; ограничим число итераций RandomisedSearchCV (например, 50).
- Интерпретируемость – бустинг сложнее для интерпретации, но для бизнес-цели (оценка стоимости) это допустимо. При необходимости можно использовать SHAP для объяснения отдельных предсказаний.
- Возможно, лучшая модель не даст значительного прироста над baseline; тогда в пилот пойдёт baseline с оговоркой, что для production нужно больше данных или признаков.

**Бизнес-проверка результата этапа:**
- После обучения основной модели проводится демонстрация Product Owner: на нескольких примерах из тестовой выборки сравниваются предсказания модели с реальными ценами. PO оценивает, насколько предсказания выглядят разумно.
- Если метрики удовлетворяют порогу, модель принимается для следующего этапа.

**Необходимый результат этапа 2:**
- Обученная baseline и основная модель.
- Сравнительная таблица метрик на валидационной и тестовой выборках.
- Выбор лучшей модели (ожидаемо – бустинг) для интеграции в сервис.
- Сохранённые модели и scaler в файлы (pickle/joblib).

### Этап 3. Подготовка инференса модели

**Цель:** разработать REST API сервис, который сможет принимать запросы с признаками объекта и возвращать предсказанную стоимость.

**Техническое решение:**
- Фреймворк: FastAPI (лёгкий, современный, с автоматической документацией).
- Эндпоинт: `POST /predict`
- Формат запроса: JSON с полями, соответствующими признакам (в том же порядке, что и при обучении). Например:
  ```json
  {
    "MedInc": 8.3252,
    "HouseAge": 41.0,
    "AveRooms": 6.984,
    "AveBedrms": 1.023,
    "Population": 322.0,
    "AveOccup": 2.555,
    "Latitude": 37.88,
    "Longitude": -122.23
  }
  ```
- Формат ответа:
  ```json
  {
    "prediction": 4.526,
    "status": "success"
  }
  ```
  или с обработкой ошибки:
  ```json
  {
    "error": "Invalid input data",
    "status": "failed"
  }
  ```
- Валидация входных данных: используем Pydantic модели с проверкой типов и допустимых диапазонов (например, возраст дома не может быть отрицательным).
- При старте сервиса загружается сохранённая лучшая модель и StandardScaler.
- Для каждого запроса:
  - Входные данные преобразуются в массив numpy.
  - Применяется стандартизация (метод transform, так как scaler уже обучен).
  - Вызывается модель.
  - Возвращается предсказание.

**Риски:**
- Несоответствие формата входных данных (например, пользователь передаст не те поля) – предусмотрена валидация и понятные сообщения об ошибках.
- Модель может давать предсказания вне допустимого диапазона (от 0 до 5.0001) – можно добавить пост-обработку (клиппинг).
- Задержки: FastAPI с лёгкой моделью (бустинг) справится за доли секунды, проблем не ожидается.

**Результат этапа 3:**
- Код сервиса (файл `app.py` или `main.py`).
- Сохранённые модель и scaler в папке `models/`.
- Инструкция по запуску в `README.md`.
- Тестовый пример запуска (curl команда).

## 3. Подготовка пилота

### 3.1. Способ оценки пилота

Пилот проводится для проверки гипотезы, что автоматическая онлайн-оценка стоимости дома повышает вовлечённость пользователей и сокращает время обработки заявок. В качестве дизайна пилота выбран **A/B-тест** на реальном трафике сайта по купле/продаже недвижимости.

- **Группа A (контрольная):** пользователи видят сайт без функции онлайн-оценки (или с текущим процессом, требующим обращения к специалисту).
- **Группа B (экспериментальная):** пользователям доступна новая функция – форма для ввода характеристик дома и получения предсказанной стоимости через наш ML-сервис.

**Способ оценки:**
1. **Бизнес-метрики:**
   - Конверсия в целевое действие (оставление заявки на продажу/консультацию) в группах A и B.
   - Время, проведённое на странице объекта (engagement).
   - Количество повторных визитов.
2. **Технические метрики:**
   - MAE модели на реальных данных (сравнение предсказаний с ценами, по которым впоследствии были совершены сделки, если такие данные доступны). Для пилота можно собирать обратную связь от пользователей (например, кнопка «Точная оценка? Да/Нет»).
   - Процент успешных запросов к API (HTTP 200) и среднее время ответа.

**Длительность пилота:** 2 недели, чтобы набрать статистически значимое количество наблюдений (минимум 1000 заявок в каждой группе).

**Ответственные:** Product Owner определяет бизнес-метрики и организует сбор данных; Data Scientist обеспечивает работу ML-сервиса и мониторинг технических метрик.

### 3.2. Что считаем успешным пилотом

Пилот считается успешным при выполнении следующих условий:

- **Бизнес-успех:**
  - Конверсия в группе B выше, чем в группе A, на **статистически значимую величину (p-value < 0.05)**.
  - ИЛИ пользователи экспериментальной группы проводят на странице в среднем на 20% больше времени.
  - Обратная связь от пользователей: не менее 70% респондентов оценивают точность предсказания как «приемлемую» или «хорошую».
- **Технический успех:**
  - **MAE модели на тестовой выборке (исторические данные) ≤ 0.4** (в сотнях тысяч долларов), что соответствует средней ошибке не более 20% от медианной цены.
  - Доступность API ≥ 99% в часы пик.
  - Среднее время ответа API ≤ 200 мс.

Если оба типа метрик достигнуты, принимается решение о расширении функциональности на весь сайт и дальнейшем развитии проекта (доработка модели, добавление новых признаков, улучшение интерфейса).

### 3.3. Подготовка пилота

**Вычислительные затраты и ограничения:**

- **Модель:** Основная модель (XGBoost) имеет размер около 5–10 МБ. Инференс одного запроса занимает менее 10 мс на одном ядре CPU.
- **Сервис:** REST API на FastAPI, асинхронный, способен обрабатывать до 100 RPS (запросов в секунду) при 2 ядрах CPU и 4 ГБ RAM (по предварительным расчётам на основе синтетических тестов).
- **Нагрузка на пилоте:** Ожидаемый трафик на новую функцию – не более 5–10 RPS в пике (исходя из среднего количества посещений сайта). Этого достаточно, чтобы сервис работал на одной виртуальной машине минимальной конфигурации.

**Что можем позволить себе на пилоте:**
- Развёртывание на облачном сервере (например, AWS t3.medium, 2 vCPU, 4 GB RAM) или на локальном сервере компании. Стоимость аренды ~ $30/мес, что приемлемо для пилота.
- Использование бесплатного SSL-сертификата для HTTPS.
- Мониторинг через простые логи и, возможно, интеграцию с Prometheus + Grafana (если есть инфраструктура). В крайнем случае – только логи.

**Уточнение параметров пилота после экспериментов с бейзлайном:**
- На этапе обучения бейзлайна и основной модели мы получим точные замеры времени инференса и потребления памяти. Если окажется, что бустинг требует больше ресурсов (например, при большом количестве деревьев), мы сможем оптимизировать модель (уменьшить `n_estimators`, применить `early_stopping`) или выбрать более лёгкую модель (например, LightGBM с `max_bin`). Это будет сделано до фиксации конфигурации для пилота.
- Если вычислительная сложность окажется выше ожидаемой, рассмотрим вариант использования модели на GPU, но в рамках пилота это не требуется.

**Ограничения:**
- Сервис не будет масштабироваться горизонтально на старте; при превышении ожидаемой нагрузки (более 20 RPS) добавим балансировщик и ещё один экземпляр сервиса.
- База данных для логирования запросов не предусмотрена, логи пишутся в stdout и собираются через систему сбора логов (ELK или аналоги) при наличии.

**Итог:** подготовка пилота включает развёртывание одного инстанса API, настройку домена (если нужно), интеграцию с фронтендом сайта через JavaScript-запросы и организацию сбора метрик для A/B-теста.
